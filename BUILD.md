# BUILD

This document describes how to build extract-sbom from source. For installing
a finished release binary, see [INSTALL.md](INSTALL.md).

## Prerequisites

- Go `1.26.2` or newer — see [go.mod](go.mod)
- `git`

## Build

```bash
go build -o extract-sbom ./cmd/extract-sbom
```

The resulting binary is statically linked (CGO disabled) and has no external
Go runtime dependencies.

## Install via go install

```bash
go install github.com/TomTonic/extract-sbom/cmd/extract-sbom@latest
```

The binary is installed into `$(go env GOPATH)/bin/extract-sbom`.

## GoReleaser (cross-platform release build)

The project uses [GoReleaser](https://goreleaser.com) to produce all release
artifacts. GoReleaser is configured in [.goreleaser.yml](.goreleaser.yml).

Install GoReleaser (requires `~> v2`):

```bash
brew install goreleaser/tap/goreleaser    # macOS
go install github.com/goreleaser/goreleaser/v2@latest  # any platform
```

Test the release build locally without publishing:

```bash
goreleaser release --snapshot --clean
```

Artifacts appear in `dist/`.

## Cutting a release

### What starts it

Pushing an annotated `v*` tag to `main`, and nothing else:

```bash
git tag -a v0.5.10 -m "v0.5.10"
git push origin v0.5.10
```

That is the only manual act in the whole chain. There is no release button to
press afterwards, no manifest to submit, no pull request to open somewhere
else. The version string comes from the tag - it is injected at link time into
`internal/buildinfo.ReleaseVersion`, which is what `extract-sbom --version`
prints - so the tag *is* the version; nothing in the source tree needs bumping
first.

`RELEASE_NOTES.md` carries hand-written notes for minor versions only
(`v0.4.0`, `v0.5.0`, …). Patch releases don't get an entry; their changelog is
generated by GoReleaser from the commit subjects, minus the `docs:`/`test:`/
`ci:`/`deps-upd:` and merge-commit noise filtered out in
[.goreleaser.yml](.goreleaser.yml).

### What happens then

The tag triggers [release.yml](.github/workflows/release.yml), which runs two
jobs in order:

1. **`release-test`** builds a Linux/amd64 binary, puts it in the container
   defined under `.github/release-test/`, and runs it there. If this fails,
   nothing is published - the tag exists but no release does.
2. **`publish`** runs GoReleaser, which builds every target, packages it, and
   uploads the results.

Twelve architecture/OS combinations are built in one pass (`linux`, `darwin`,
`windows` × `amd64`, `arm64`), always with `CGO_ENABLED=0`. That flag is load
bearing, not cosmetic: on an amd64 runner, `GOARCH=amd64` is not a
cross-compile, so cgo would stay enabled and produce a binary dynamically
linked against the runner's glibc - which then fails to start on musl systems
like Alpine, while every other target works. This has actually happened in a
sibling project.

### Where each artifact ends up

| Artifact | Published to | By whom | When | How users get it |
|---|---|---|---|---|
| `.tar.gz`, `.zip`, `checksums.txt` | GitHub Release on this repo | GoReleaser | during the tag run | manual download |
| `.deb`, `.rpm`, `.apk`, `.pkg.tar.zst` | GitHub Release on this repo | GoReleaser | during the tag run | manual download, **or** the repository below |
| Homebrew cask | [`TomTonic/homebrew-tap`](https://github.com/TomTonic/homebrew-tap) | GoReleaser, pushing over SSH | during the tag run | `brew install TomTonic/tap/extract-sbom` |
| apt / dnf / zypper / pacman / apk indices | [pkg.tomtonic.de](https://pkg.tomtonic.de) | [`TomTonic/pkg-repo`](https://github.com/TomTonic/pkg-repo), separately | within the hour | `apt install extract-sbom` etc. |

The GitHub Release is the single source of truth. Everything else - the cask,
every Linux index - points back at those assets by URL and SHA-256. Nothing
re-builds the binary downstream.

### How the Linux repository picks it up

`pkg-repo` is not triggered by this repository; it polls. Its
`publish.yml` runs **hourly at :17** (plus `workflow_dispatch` and a
`repository_dispatch: refresh` event that nothing currently sends). On each
run it reads its own `manifest.json` - which lists `TomTonic/extract-sbom`
among the tools - calls `scripts/fetch-releases.sh` to download the **latest
and the previous** non-draft, non-prerelease release's package assets, rebuilds
all five index formats from scratch, signs them, and deploys the result to
GitHub Pages.

Three consequences worth knowing:

- A new release shows up for `apt`/`dnf`/`pacman`/`apk` users **within an
  hour**, not immediately. To publish sooner, run the workflow manually from
  the `pkg-repo` Actions tab.
- Only the two most recent releases are carried in the repository. Older
  versions stay downloadable from GitHub Releases, but the package repository
  will not offer them.
- Only the *index* is signed, not each individual package. Package integrity
  comes from the checksums recorded in that signed index.

If a release is missing from the repository, check in this order: is the
GitHub release marked draft or prerelease (`fetch-releases.sh` skips both), did
the hourly run happen yet, did the publish workflow fail.

### Credentials

GoReleaser writes to exactly one repository outside this one:
`TomTonic/homebrew-tap`, where the cask lives. That push goes over SSH using a
**deploy key**, held in the repository secret `HOMEBREW_TAP_DEPLOY_KEY`. A
deploy key is used deliberately instead of a personal access token: it is
valid for that one repository and can be revoked on its own, whereas any PAT
able to write to the tap would be an account-wide credential. The key is
passphrase-less because the workflow runs unattended - GoReleaser rejects
passphrase-protected keys outright. Rotating it means generating a new key
pair, replacing the deploy key on the tap, and updating the secret here.

Everything else uses the workflow's built-in `GITHUB_TOKEN`. The signing keys
for the Linux indices live in `pkg-repo`, not here - see that repository's
`SUCCESSION.md` for their custody and rotation.

### Windows ships as a plain zip

No WinGet manifest, no Chocolatey package, no Microsoft Store listing. That is
a deliberate choice, not an omission. Every third-party index pins the
installer URL and its SHA-256 permanently, and none of them lets the publisher
withdraw a version once it is accepted: `winget-pkgs` needs a pull request to
Microsoft to remove one, and Chocolatey states plainly that "once approved,
there is no reject". Since withdrawing a bad release has to stay possible for a
security tool, this project only publishes through channels it controls
end-to-end.

### The rule that follows from all of this

**Published release assets are never deleted or replaced, only superseded by a
new version.** The cask and all five Linux indices reference assets by URL and
checksum; removing one breaks every install that already points at it. If a
release turns out to be wrong, tag a new one, and - if the bad version must be
taken out of circulation - mark the old GitHub release as a prerelease, which
makes `fetch-releases.sh` skip it on the next hourly run without breaking
anything that already resolved it.
